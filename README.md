# GridScope Studio

A lightweight energy analysis studio for turning household billing or meter CSVs into clean metrics, charts, tables, and short observations.

The main report opens in a browser and lets people upload their own CSV locally. The reproducible pipeline underneath still uses R, SQLite, and reusable SQL query files, so the same analysis can be rerun from the command line — and both paths now agree, because they share the same date handling, the same tier-split constants, and the same anomaly rule.

## Quick Start

```sh
make test      # R + browser test suites
make demo      # build the demo report
```


Generate the demo portfolio report:

```sh
make demo
open output/report.html
```

Analyse your own CSV:

```sh
make custom INPUT=data/sample_energy_upload.csv OUTPUT=output/custom-report.html
open output/custom-report.html
```

Verify the full pipeline:

```sh
make verify
```

## CSV Columns

Required:

- `day` or `date`
- either `grid_import_kwh` or `total_kwh`, or the tiered fields `peak_kwh`, `shoulder_kwh`, and `offpeak_kwh`

Optional:

- `household_id`
- `neighbourhood` or `suburb`
- `solar_export_kwh`
- `estimated_bill`

The browser upload flow accepts the same columns and produces graphs immediately in the page.

## Requirements

- R 4.x (base only — no packages required, including for the tests)
- SQLite CLI: `sqlite3`
- Node 18+ for the browser test suite (`make test-js`)

On macOS, SQLite is usually already available. Check with:

```sh
sqlite3 --version
```

## Unusual Day Detection

Each household is compared against **its own** median daily grid import, scaled
by its own median absolute deviation — the Iglewicz-Hoaglin modified z-score,
flagged at |z| >= 3.5.

This replaced a rule that compared every reading to the mean of all readings and
flagged anything outside ±50% of it, which had two failure modes:

- the mean was inflated by the very spikes it was meant to find, so one extreme
  day hid the rest;
- across several households, a large house read as permanently "high" and a
  small one as permanently "low".

On the bundled sample (1,460 rows, four households, a year of readings) the old
rule flagged 169 rows — mostly differences in house size. The current rule
flags the three genuine events in the data and nothing else.

Households with fewer than five readings, or a perfectly flat series, fall back
to a ±50% rule against their own median, and the `method` column says which was
used.

## Analysis Included

- Monthly grid import and solar export trends
- Load mix across peak, shoulder, off-peak, and solar export
- Group comparison by neighbourhood or suburb
- Cost rollups when a bill or cost column is supplied
- Data quality summary with record, day, and household counts
- Unusual usage day detection for spikes and dips
- Savings opportunity recommendations for peak shifting, solar, and spend review
- Browser dark mode and JSON export for personal analysis

## Browser Tools

The demo report includes:

- Sample data loader for quick testing

## CSV Handling

- **Date format is decided once per column**, not per row, so a file mixing
  `1/2/2024` and `13/2/2024` is read under a single convention instead of two.
  Ambiguous day/month columns are read day-first and the report says so.
- **Dates are calendar days, never instants.** The browser path used
  `toISOString()` on local-midnight dates, which shifted every day backwards in
  any timezone ahead of UTC.
- **Values that are not numbers are counted, not silently zeroed.** Blank cells
  still mean "no reading"; text does not.
- **A modelled tier split is labelled as one.** If your file has only a total
  kWh column, peak / shoulder / off-peak are estimated at 44/34/22% and every
  figure that depends on them is flagged as an estimate in the report.

## Testing

```sh
make test        # both suites
make test-r      # R unit tests + end-to-end SQL against a temp database
make test-js     # browser analysis logic under Node
```

The R suite needs base R only. Both suites run in CI, which also rebuilds the
sample dataset and fails if it is not reproducible.
